# R438 · 把零的构造从每轮手写变成 `lib` —— 而回溯发现「62 个轮次」其实是 **11 处**

⚠ **CLOSURE + 一次 FRONTIER 测量**(分母我事前不知道)。

## ① `lib/nulls.py` —— 三个构造器,各自自带对照
| 函数 | 它防的错 |
|---|---|
| `perm_in(v, mask, seed)` | **掩码内**打乱,保住缺失格局 —— 三次栽跟头的那一个 |
| `sham_control(x, r, mask, seed)` | 与 `x` 相关度指定、与结局无关的合成控制(`offset` 地板) |
| `row_perm(cols, mask, seed)` | **整行**打乱,保住列间相关(多列联合的零) |

`controls()` **6/6 通过**:含 NaN 的输入仍给有限统计量 · 缺失格局不变 · 确实打乱了 ·
合成相关度 0.404 ≈ 指定的 0.40 · 整行打乱保住 0.6004→0.6004 ·
**负对照:逐列独立打乱把它破坏成 −0.009**(证明这个检验有分辨力)。

## ③ ⚠ 而「危险的那一种」不是 62 个轮次,是 **11 处**
第一版的正则同时匹配了 `permutation(len(v))]`,把 **62** 个轮次标红。
**打印原文分类后**(`#374b` 的规矩):**索引/下标(安全)占绝大多数,真正打乱数据列的只有 11 处。**
> **一个审计工具的假阳性,和它审计的那类错,是同一个方向的错**(`#382c` 同一条)。

## ④ ★ 而是否成 bug,**不取决于那一行**
**决定性演示**:一列 15,503 长、**只有 1 个 NaN**,掩码覆盖 43% ->
整数组打乱 400 次里 **167 次(42%)** 掩码内出现 NaN;`perm_in` **0/400**。
**一个 NaN 就够,而 `np.percentile` 遇到一个 NaN 就返回 NaN。**

**⇒ 之所以有些轮次活了下来,是因为它们的拟合函数**重新按有限性掩码**(如 `R414` 的 `coef`),
而 `R429`/`R437` 的没有。**
> **决定它是不是 bug 的,不是那一行,是下游有没有重掩** ——
> 这也是为什么它**看起来是间歇的**,而间歇的错最难靠「记住」来防。
> `lib.nulls.perm_in` 把这个依赖**整个拿掉**:它不管下游做什么。
